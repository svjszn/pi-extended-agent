# Subagents

A subagent is a separate agent run with its own instructions, tool selection,
and context. It receives one task, works on it without adding its transcript to
your conversation, and returns a single report.

Open `/agents` to browse what is configured, create an agent, or run one:

```text
/agents
/scout find every caller of parseAgent
/lens
/lens review the changes in HEAD~1..HEAD
/agents stop
```

`/scout TASK` requires a research question. `/lens` reviews the current staged,
unstaged, and untracked changes; `/lens TASK` selects a specific review scope.
Both use the same overrides, permissions, and cancellation as
`/agents run NAME TASK`.

After a manual run, its final report is passed to the main agent, which writes
the conclusions as a normal chat response in your conversation's language.
The handoff includes findings, code references, checks, limitations, and open
questions. The raw report is hidden from the terminal but kept in the parent
session for later questions and resume. If the main agent is already working,
the report waits as a follow-up. Cancelled and failed runs do not start a summary.

While a subagent runs, the existing Working line immediately above the input
shows its name, animated indicator, elapsed time, current activity or tool, and
number of tool calls. Concurrent runs share that line: the most recently started
agent is shown with a count of other active runs. The status clears when the run
finishes, fails, or is cancelled. Activity shows no reasoning, tool arguments,
or tool results, and adds no messages to the parent context.

The model can also delegate on its own with the `task` tool when a task is
self-contained. The report returns through that tool, and the main agent uses
it to continue the task and explain its conclusions. Reports are bounded to
24,000 characters; intermediate work stays in the child context.

## Built-in Agents

Two agents are available immediately, including with an empty profile:

| Agent | Purpose | Tools |
| :--- | :--- | :--- |
| `scout` | Locate implementations, trace callers and data flow, and report concise findings with file and line references | read, find, grep, ls |
| `lens` | Independently review changes for actionable bugs, regressions, security and compatibility issues | read, find, grep, ls, bash |

Both inherit your current model and reasoning effort. Scout returns the evidence
needed for the parent's next step. Lens prioritizes concrete findings by severity,
with a triggering condition, impact, and precise code references; it reports when
there are no actionable findings or when verification is incomplete.

Lens is instructed to use shell commands only for read-only Git inspection and
to leave changes and test execution to the parent. Shell calls still use the
current permission checks. In Deny or Plan mode, shell access is blocked;
provide a diff or explicit files to review with the available readers. Lens must
report any review scope it cannot establish.

The parent prompt receives only names and descriptions. Full agent instructions
and intermediate tool results stay in the child context; only its final report
returns to the conversation. Bundled definitions do not create profile files.

Definitions are resolved in this order: **trusted project → profile → built-in**.
Press **e** on a built-in agent to save an editable override, defaulting to the
global scope. Change the editor's scope line to `project` for a project override.
Deleting an override restores the next definition in that order. Bundled defaults
cannot be deleted. An unreadable override is reported while a lower-priority
definition remains available.

## Define an Agent

Definitions are Markdown files with frontmatter, in either of two scopes:

- `.pi/agents/NAME.md` in the project, shared through your repository
- `AGENT_DIR/agents/NAME.md` in your profile, available everywhere

A project definition shadows a profile definition with the same name, the way
project settings do. Project definitions are ignored until you approve the
project, so an untrusted repository cannot add instructions or tool selections.

```markdown
---
name: researcher
description: Reads code and reports findings without changing files
tools: read, grep, find, ls
---

Investigate the question and report what you found, with file paths and line
numbers. Do not change files.
```

`description` tells the model when to delegate, so write it for that purpose.
`tools` is optional: omit it to inherit the engine's default selection, list
names or `*` patterns to narrow it, or use `tools: []` for no tools at all.
`model` is optional and keeps the current model when absent. The file body is
the agent's instructions; it is added to Pi's own system prompt rather than
replacing it.

Agent names use lowercase letters, digits, and single hyphens. Press **n** in
`/agents` to create one, **e** to edit, and **d** to delete. The first editor
line selects the scope. A definition that cannot be read is listed by name so
the remaining agents keep working.

## Permissions

A subagent never gets more access than you have granted in the current session.
It runs the same checks your own tool calls do:

| Mode | Subagent behavior |
| :--- | :--- |
| Allow | Runs with its own tool selection, without prompts |
| Ask | Each change, shell command, and external tool needs your approval |
| Deny | Offered only the built-in read, find, grep, and ls tools |
| Plan mode | Research only, until you run `/plan execute` |

In Ask mode the approval dialog names the subagent and offers **Deny**, **Allow
once**, and **Allow for this run**. Denial stays the default, and the run-wide
choice is never preselected: it covers the rest of that single subagent run and
nothing else. One dialog appears at a time, whether the request comes from your
own tool calls or from a subagent.

In Deny and Plan mode the selection is narrowed before the run starts, and
never beyond what the definition lists: an agent that asks only for `bash` is
offered nothing in those modes.

## Limits

A subagent cannot ask you questions, cannot start another subagent, and does
not load your commands, project memory, or skills. Its run is bounded to 100
tool calls. Its session is held in memory, so it writes no transcript to your
profile. Interrupting the parent run cancels the subagent.
For a manual `/agents run`, press **Esc** or **Ctrl+C**, or use `/agents stop`.
Closing or replacing the parent session cancels its children and waits for them
to finish before the session is replaced. Changing permissions or plan mode
also cancels active subagents, so an earlier grant cannot outlive that policy.
